# Schema Migrations

Every `@Database(version = N)` bump needs a migration path — a `Migration`,
an `@AutoMigration`, or an explicit destructive fallback — before it ships.
Skip all three and every existing install throws the moment it opens the
upgraded database:

> "A migration from $oldVersion to $newVersion was required but not found.
> Please provide the necessary Migration path via
> RoomDatabase.Builder.addMigration(...) or allow for destructive migrations
> via one of the RoomDatabase.Builder.fallbackToDestructiveMigration*
> functions."

Confirmed against `RoomConnectionManager` in the `androidx.room3:room3-runtime`
source, not a guide page — the message itself says `addMigration`, singular,
even though the builder method is `addMigrations`. A fresh install never sees
this: Room creates the schema at the current version directly, with no
version to migrate *from*, which is exactly why a missing migration ships
unnoticed until an existing user updates.

Room 3 dropped `SupportSQLiteDatabase` from this callback. A `Migration`'s
`migrate` function, and `AutoMigrationSpec.onPostMigrate`, now receive an
`androidx.sqlite.SQLiteConnection` — the same driver connection type behind
[room-setup.md](room-setup.md)'s `setDriver(...)` and
[schema-dao.md](schema-dao.md)'s `useWriterConnection` transactions.

## Schema Export

`@Database.exportSchema` defaults to `true`. With no schema directory
configured, the Room compiler refuses to proceed:

> "Schema export directory was not provided … apply the Room Gradle plugin
> (id 'androidx.room3') OR set exportSchema to false."

The normal fix is the Gradle extension [room-setup.md](room-setup.md) already
wires up:

```kotlin
room3 {
    schemaDirectory("$projectDir/schemas")
}
```

Commit the JSON files that land there — one per version, per database —
because everything past this section reads them: `@AutoMigration` diffs two
of them to generate SQL, and `MigrationTestHelper` below opens them to build
the old-version database it migrates from.

`exportSchema = false` is a legitimate choice, not a workaround, for a
database that is a pure cache with no upgrade story worth diffing across
versions. Taking it means giving up `@AutoMigration` entirely:
`@Database.autoMigrations` requires `exportSchema = true`, since an automatic
migration is generated by diffing two exported schemas that, with the flag
off, no longer exist.

## Automatic Migrations

For a change Room can express as a plain schema diff — a new nullable
column, a new table — `@AutoMigration` writes the `Migration` for you:

```kotlin
@Database(
    entities = [ItemEntity::class],
    version = 2,
    exportSchema = true,
    autoMigrations = [AutoMigration(from = 1, to = 2)],
)
@ConstructedBy(AppDatabaseConstructor::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun itemDao(): ItemDao
}
```

Here version 2 only adds a nullable `notes: String?` to `ItemEntity` — Room's
schema diff sees a new column with an implicit `NULL` default and needs no
help.

A rename or a delete is ambiguous from a diff alone: Room cannot tell "column
removed, unrelated column added" from "column renamed," so it refuses to
guess and requires an `AutoMigrationSpec` that names the change. Evolving
`ItemEntity` again, this time renaming `name` to `title`:

```kotlin
@Database(
    entities = [ItemEntity::class],
    version = 3,
    exportSchema = true,
    autoMigrations = [
        AutoMigration(from = 1, to = 2),
        AutoMigration(from = 2, to = 3, spec = AppDatabase.Spec2To3::class),
    ],
)
@ConstructedBy(AppDatabaseConstructor::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun itemDao(): ItemDao

    @RenameColumn(tableName = "items", fromColumnName = "name", toColumnName = "title")
    class Spec2To3 : AutoMigrationSpec
}
```

`@RenameColumn`, `@RenameTable`, `@DeleteColumn`, and `@DeleteTable` (package
`androidx.room3`) are the only vocabulary Room accepts here; stack more than
one on the same spec class when several tables changed between the same two
versions. The boundary is exactly this: Room derives SQL by diffing two
exported schemas, so a type change or any transformation of existing data —
the kind of change the next section handles — is never expressible as a
spec, however it's annotated.

## Manual Migrations

Room's diff can add a column; it cannot populate it from another column's
value. That needs a manual `Migration`, registered on the builder instead of
listed in `autoMigrations`. Continuing the same entity, version 4 adds a
`NOT NULL` `priority` column and backfills it from the existing `status`:

```kotlin
val MIGRATION_3_4 = Migration(startVersion = 3, endVersion = 4) { connection ->
    connection.executeSQL("ALTER TABLE items ADD COLUMN priority INTEGER NOT NULL DEFAULT 0")
    connection.executeSQL("UPDATE items SET priority = 1 WHERE status = 'URGENT'")
}
```

```kotlin
// commonMain
fun createAppDatabase(builder: RoomDatabase.Builder<AppDatabase>): AppDatabase =
    builder.addMigrations(MIGRATION_3_4).build()
```

`Migration(startVersion, endVersion, migrate)` is the top-level builder
function `room3-runtime` exports as a lambda-friendly alternative to
subclassing `Migration` directly; both compile to the same
`migrate(connection: SQLiteConnection)` shape. `connection.executeSQL(...)`
is a suspend extension from `androidx.sqlite:sqlite-async` (package
`androidx.sqlite.async`) — confirmed by reading that module's source, not a
guide page. `room3-runtime`'s own `commonMain` depends on it as
`implementation`, not `api`, so it is not guaranteed on a consumer's
classpath just by depending on `room3-runtime`; add
`androidx.sqlite:sqlite-async` to `commonMain` explicitly if `executeSQL` or
`prepare` don't resolve, at the same `androidx.sqlite` version pinned in
[room-setup.md](room-setup.md)'s coordinate table.

`migrate` runs inside a transaction Room opens for you — the whole set of
migrations chosen for one upgrade can share it — so there's no
`useWriterConnection` call to write here; that API from
[schema-dao.md](schema-dao.md) is for application code, not migration
bodies.

## Destructive Fallback

```kotlin
builder.fallbackToDestructiveMigration(dropAllTables = true)
```

`dropAllTables` regained a default of `true` in `3.0.0-alpha02` — the release
notes record it as "added a default parameter value to dropAllTables in the
fallbackToDestructiveMigration APIs" — so the zero-argument call
`fallbackToDestructiveMigration()` compiles again, and nothing at compile
time stops it from running against a database with data worth keeping. This
is a cache-eviction strategy wearing a migration's name: dropping and
recreating every table, discarding every row. Reach for it only where every
row is re-fetchable from the network or recomputable locally, declare it in
exactly one place — the builder wiring beside `addMigrations` — with a
comment saying why it's safe there.

`fallbackToDestructiveMigrationOnDowngrade(dropAllTables = true)` narrows
this to downgrades only — installing an older build over a newer database,
which by definition has no forward migration path.
`fallbackToDestructiveMigrationFrom(dropAllTables = true, vararg startVersions: Int)`
narrows it further, to specific starting versions, while every other missing
path still throws the runtime message from the top of this file. These two
are the defensible middle ground between "always destroy on any gap" and
"never destroy."

## Testing a Migration

`MigrationTestHelper` (package `androidx.room3.testing`, artifact
`androidx.room3:room3-testing`) is declared as an `expect class` in
`commonMain`, with `actual` implementations in `androidMain`, `jvmMain`,
`nativeMain`, and `webMain` — confirmed by reading the module's source tree,
not the guide pages, which only ever show the Android case.
`createDatabase(version: Int): SQLiteConnection` and
`runMigrationsAndValidate(version: Int, migrations: List<Migration>): SQLiteConnection`
are the two members the `expect class` declares, so both are visible from
`commonTest`.

The constructor is not one of them. Each platform's `actual` class defines
its own, and they don't match: the `jvmMain` actual takes
`schemaDirectoryPath: Path, databasePath: Path, driver: SQLiteDriver,
databaseClass: KClass<out RoomDatabase>` and extends JUnit4's `TestWatcher`;
the `androidMain` actual instead takes `instrumentation: Instrumentation,
file: File, driver: SQLiteDriver, databaseClass: KClass<out RoomDatabase>`.
There is no shape `commonTest` can construct once and share — **migration
tests live in the platform test source set**, `jvmTest` for desktop or
`androidTest` (instrumented) for Android, each as a JUnit4 rule:

```kotlin
// jvmTest
import androidx.room3.testing.MigrationTestHelper
import androidx.sqlite.driver.bundled.BundledSQLiteDriver
import kotlin.io.path.Path
import kotlin.io.path.createTempFile
import kotlinx.coroutines.test.runTest
import org.junit.Rule
import org.junit.Test

@get:Rule
val migrationHelper = MigrationTestHelper(
    schemaDirectoryPath = Path("schemas"),
    databasePath = createTempFile("test.db"),
    driver = BundledSQLiteDriver(),
    databaseClass = AppDatabase::class,
)

@Test
fun migrate3To4_backfillsPriorityFromStatus() = runTest {
    migrationHelper.createDatabase(3).apply {
        // version 3 already has `title`, not `name` — the AutoMigrationSpec above renamed it
        executeSQL("INSERT INTO items (id, title, status, createdAt) VALUES ('1', 'Ticket', 'URGENT', 0)")
        close()
    }
    val migrated = migrationHelper.runMigrationsAndValidate(4, listOf(MIGRATION_3_4))
    migrated.prepare("SELECT priority FROM items WHERE id = '1'").use { statement ->
        check(statement.step())
        check(statement.getLong(0) == 1L)
    }
    migrated.close()
}
```

`runMigrationsAndValidate` does two things in one call: it runs the given
migrations, then validates the resulting live schema against the exported
schema for `version`, failing the test if they diverge — a rename applied to
only one of two duplicate columns, say. Both functions read from the same
`schemaDirectoryPath` the Gradle plugin wrote to, which is why Schema Export
above insists the JSON gets committed: a migration test against an
uncommitted schema only ever ran on the machine that generated it.

This is the only file in the skill that names `MigrationTestHelper`; treat
this section, not the general testing reference, as where migration tests
are documented.
